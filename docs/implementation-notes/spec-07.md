# Spec 07 implementation notes

Deliberate choices made while implementing Spec 07 (Ticket Links and Estimates). Reviewers: treat these as decided unless one contradicts the spec or an ADR.

## 07-01 Schema and glossary

- **One generated migration.** `packages/db/drizzle/0013_ticket_links_and_estimates.sql` and its snapshot and journal entry come from `pnpm db:generate` (drizzle-kit), not hand-written SQL, so meta stays consistent. It holds both the `estimate` column and the `ticket_links` table, so later Spec 07 cards add no migration of their own unless they need a schema change.
- **Stored kinds live in `packages/shared`.** `ticketLinkKinds` (`blocks`, `relates_to`) sits next to `ticketTypes` and the other enum tuples, and the `ticket_link_kind` pgEnum is built from it. `blocked_by` is not a stored kind: it is an input that 07-03 stores as the reverse Blocks row, so it is left for the `linkTicketsInput` schema.
- **No `updated_at` on `ticket_links`.** A Link is never edited: changing its kind is remove and add (spec, "one Link per pair"). Only `created_at` is stored, as the spec lists.
- **Creator columns follow `tickets`.** `created_by_user_id` / `created_by_agent_id` reuse the `actorUser()` / `actorAgent()` helpers (restrict on delete, ADR-0007) with an exactly-one check, `ticket_links_one_creator`, matching `tickets_one_creator`.
- **The pair index uses `least`/`greatest` on the text ids.** `ticket_links_pair_unique` is a unique expression index on `least(from, to), greatest(from, to)`, so a second Link between the same two Tickets fails whatever its kind or direction. It also serves the "is there already a Link between these two" lookup. The ids use the default collation; that only matters for which id is "least", and any fixed order makes the pair unique. 07-03 should store a Relates to row in the same order (`from` = the lesser id under Postgres's comparison) if it wants a canonical row, or simply look the pair up through `least`/`greatest`.
- **No separate `company_id` index.** Lookups go through a Ticket (`from_ticket_id` and `to_ticket_id` are each indexed). The cycle check walks Blocks Links from a Ticket id, so it uses the `from_ticket_id` index. `company_id` is kept for the Company boundary and the cascade on Company delete, like `comments`.
- **Estimate check allows null.** `tickets_estimate_range` is `estimate between 0 and 100`; a null estimate makes the check null, which Postgres treats as passing, so blank stays allowed. Whole numbers come from the `integer` type; the domain refuses fractions before they reach the database.
- **Glossary.** Estimate, Ticket Link, Blocks, Relates to, and Blocked are added at the end of Board, after Claim, with the spec's _Avoid_ lists (Blocked has none in the spec, so none is added). Parent's _Avoid_ of "link" is unchanged. The new _Avoid_ terms (size, weight, relation, references, and so on) are now enforced by `scripts/check-copy.mjs`; no existing copy tripped them.
- **No new tests.** This card has no behavior to drive through the harness or the browser, and the spec rules out asserting on table rows. The existing suite runs every migration in `apps/server/test/global-setup.ts` and stays green. 07-02 and 07-03 test the constraints through REST and MCP.

## 07-02 Estimate over REST and MCP

- **One shared `ticketEstimate` schema.** `packages/shared/src/tickets.ts` exports `ticketEstimate` (named like `ticketType` and `ticketStatus`, not a bare `estimate` that would shadow local variables in the web app) with the one message "Estimates are whole numbers from 0 to 100." on every failure: wrong type, fraction, below 0, above 100. 07-06 can reuse it client-side.
- **Strict numbers, no coercion.** A JSON string such as `"3"` is refused, like any other non-number, rather than coerced. The REST body and MCP arguments are both JSON, so a real number is always available to the caller.
- **Create defaults to null in the schema.** `createTicketInput.estimate` is `nullable().default(null)`, so the domain always writes an explicit value and a missing field and an explicit null mean the same thing (blank) on create. On update the field is `nullable().optional()`: absent leaves it alone, null clears it.
- **No domain code beyond the pass-through.** `updateTicket` already spreads the parsed fields into `changedFields` and `saveTicket`, so `estimate` lands in the `ticket.updated` diff (`{ estimate: { from, to } }`) and a no-op write records nothing, with no Estimate-specific branch. Only `createTicket` (the insert) and `ticketViews` (the view) name the column.
- **`ticketView.estimate` is required and nullable**, not optional, so every response says whether a Ticket is sized. `blocked` and `blockedByCount` are left to 07-04, which computes them.
- **MCP description lives once.** `estimateDescription` in `apps/server/src/mcp/params.ts` is attached to the shared schema on both `create_ticket` and `update_ticket`, so the wording the spec fixed cannot drift between them. `update_ticket`'s description now lists estimate among the fields it changes.
- **"N pts" for every value, including 1 and 0.** The spec writes the badge as number plus "pts"; "1 pts" reads oddly but keeps one form Agents can match, and 0 shows as "0 pts" so a zero-point Ticket stays distinct from a blank one.
- **get_ticket always shows an Estimate line.** The ticket line in lists and on the board shows "N pts" only when set (spec), but get_ticket's fact list adds `Estimate: N pts` or `Estimate: none`, matching how it already says `Parent: none`. This mirrors Ticket detail in the web UI, which always shows the Estimate or that it is blank (story 9).
- **Tests in a new `apps/server/test/estimate.test.ts`** rather than spread across `tickets.test.ts`, `archive.test.ts`, and the MCP tests, to keep the Estimate rules readable in one place and to avoid conflicts with 07-03 working in parallel. REST rules run as both a User and an Agent. MCP only authenticates Agents, so the MCP tests act as the Agent and read the result back as the User over REST. Archive and restore run as the User only, since Agents can't archive (Spec 02).

## 07-03 Ticket Links over REST

- **Module and routes.** `packages/domain/src/ticket-links.ts` owns every Link rule (`linkTickets`, `unlinkTickets`, `listLinks`); the three routes in `apps/server/src/routes/tickets.ts` only parse and shape. `POST` answers 201 with `{ link }`, `DELETE` 204, `GET` `{ links }`, matching the Comment and Ticket routes.
- **`ticketLinkView` is flat.** The other Ticket's `key`, `projectKey`, `title`, `type`, `status`, and `archived` sit beside `kind`, `createdBy`, and `createdAt`, rather than nested under a `ticket` object, as the spec lists them. `archived` is a boolean ("whether it is archived"), not a timestamp.
- **`ticketLinkViewKinds` doubles as the group order.** `["blocked_by", "blocks", "relates_to"]` is both the input enum for `linkTicketsInput.kind` and the order `GET` lists in. Within a group, Links are ordered by the other Ticket's Project Key, then number, so the list is stable when the fake clock gives every Link the same `createdAt`.
- **Rule order and status codes.** Not found (either Ticket, or another Company) comes first, then self-link (400, `invalid`, like the hierarchy rules), then archived (409, `conflict`, like the existing "Archived tickets can't be moved/assigned/claimed"), then an existing Link (409), then a Blocks cycle (409). Archived is checked before the duplicate so an archived Ticket reads as "Restore CB-2 before linking it." whatever Links it already has.
- **A "direct" cycle is reported as the existing Link.** With one Link per pair, "CB-2 blocks CB-1" while "CB-1 blocks CB-2" exists is a duplicate pair before it is a cycle, so it gets "CB-1 already blocks CB-2." The cycle message only appears for chains of three or more Tickets: "CB-3 can't block CB-1 because CB-1 already blocks CB-3 through CB-2."
- **The duplicate message names the existing Link in its own direction.** A Blocks Link reads from its blocker ("CB-1 already blocks CB-2.") whichever side the request came from; a Relates to Link reads from the requesting Ticket ("CB-2 already relates to CB-1.").
- **Copy avoids the bare word "link".** GLOSSARY.md keeps "link" as an _Avoid_ term for Parent, and `scripts/check-copy.mjs` flags `link`/`links` in user-facing strings. The messages use "linked" and "linking" ("A ticket can't be linked to itself.", "CB-1 and CB-2 aren't linked.") instead of adding allowlist entries.
- **Cycle query.** One recursive CTE walks Blocks Links in the Company from the would-be blocked Ticket, carrying the path, and stops on any id already in the path. It returns the shortest path back to the would-be blocker, whose middle Tickets are named in the message. Paths are enumerated, not just reached ids, so a dense graph costs more; boards are small enough that this is not a concern yet.
- **Locking.** Both Tickets are resolved by key (so not found and visibility come from `findTicket`), then locked together with one `select ... order by id for update`, so two changes to the same pair always lock in the same order. `withActivity`'s per-Company advisory lock already serializes changes, so the row locks are belt and braces, and the duplicate check relies on that serialization instead of catching the pair index's unique violation.
- **Relates to is stored with `least`/`greatest` in SQL.** The canonical order comes from Postgres's comparison at insert time, as the 07-01 note suggests, rather than comparing ids in JavaScript. The pair lookup also goes through `least`/`greatest`, so it uses `ticket_links_pair_unique`.
- **Activity payload.** `ticket.linked` and `ticket.unlinked` carry `{ kind, ticket }`: the kind as seen from the Ticket the Activity is on, and the other Ticket's key. `ticket` (not `ticketKey`) avoids reading as the Activity's own Ticket, which `ticket.deleted` stores as `payload.ticketKey`. The requesting Ticket's Activity is recorded first. `ticket.unlinked` records the kind the Link had.
- **Archived counterparts are listed.** `GET` includes Links to archived Tickets, marked `archived: true`; removal works with either Ticket archived. Archive and restore leave Links untouched; the existing cascade removes them on hard delete, so 07-03 adds nothing to `archive.ts`.
- **No Blocked here.** Linking and unlinking a Blocks Link don't compute or record `ticket.blocked`/`ticket.unblocked`; 07-04 adds that around these same services.

## 07-04 Blocked state and Claim

- **Two derivations, one rule.** `ticketViews` gets each Ticket's open blockers with one batched query (`openBlockers`), next to the batched Actor and Parent lookups it already makes, rather than a column added to `selectTickets`, which many callers use for locking and rule checks that don't need it. Filters use `isBlocked()`, a correlated `exists` over `tickets`, in the list query and in Claim's conditional update. Both live in `ticket-store.ts` and state "open" the same way (not Done, not archived); a comment ties them together.
- **`blockedByCount` counts every open blocker,** in any Project of the Company. Every User sees every Project today (`canSeeProject`), so no blocker is hidden from the caller.
- **The `blocked` filter is a query string,** so it takes `true` or `false` and refuses anything else with "Use blocked=true or blocked=false.", following "Use archived=include." Absent means both. It is applied in SQL before paging, like the other filters, so pages stay full.
- **Claim checks Blocked last.** The condition joins the existing conditional update (`not exists` an open blocker), so the check and the Claim are one statement in the same transaction. When the update matches nothing, archived, held, and Done are reported first, and Blocked only when the Ticket would otherwise be claimable: an Agent told "CB-7 is already held by Claude-2" learns the more useful fact.
- **The Claim conflict also carries `blockers`,** the open blockers' keys in key order, beside `error`, as the held conflict carries `assignee`. 07-05 can use it without parsing copy. Keys are ordered by Project Key then number, so the message is stable ("CB-7 is blocked by CB-3 and CB-5.").
- **`listInWords` moved to `words.ts`.** The cycle message in 07-03 and the Claim message both list keys as "A, B, and C"; the helper is not exported from the domain package.
- **Transitions are a watch, not a diff of the whole board.** `watchBlocked(tx, ids, cause)` notes the Blocked state of the given Tickets before the change and returns a function that, after the change, records `ticket.blocked` or `ticket.unblocked` on each one that flipped. `watchDependents(tx, blocker)` watches every Ticket the blocker blocks. Only Tickets whose state actually flipped get Activity, so a dependent with another open blocker records nothing.
- **Which changes watch.** A move watches only when it crosses Done (`done` into, `reopened` out of); a move between open Statuses can't flip anything and skips the query. Archive (`archived`), restore (`restored`), and hard delete (`deleted`) always watch; a Done blocker being archived finds no flips. Linking and unlinking watch only for Blocks (`linked`, `unlinked`); Relates to never changes Blocked.
- **Payload is `{ ticket, reason }`.** `ticket` is the causing Ticket's key, matching `ticket.linked`'s `ticket` field (the other Ticket, not the Activity's own). For a Blocks Link added or removed, the cause is the blocker, from whichever side the request came.
- **Activity order.** The causing change's own Activity comes first (`ticket.moved`, `ticket.archived`, `ticket.restored`, `ticket.deleted`, or both `ticket.linked`/`ticket.unlinked`), then the transitions, ordered by the dependent's key. On a stream this reads as cause then effect.
- **Hard delete watches before deleting.** Dependents are found while the Links still exist; the cascade then removes them, and the after state is read once the row is gone. `ticket.unblocked` records the deleted Ticket's key as the cause, which is all that is left of it.
- **Archived dependents get transitions too.** Blocked is derived for every Ticket, archived or not, and an archived dependent's view flips with its blocker. Recording the Activity keeps its Timeline consistent with what its view says. A reviewer may prefer to skip archived dependents; that is a one-line filter in `watchBlocked`.
- **Project deletion records no transitions.** `deleteProject` cascades every Ticket in the Project and their Links. A Ticket in another Project that one of them blocked becomes unblocked (its derived view is correct) but records no `ticket.unblocked` and streams no snapshot. The ticket names moves, archive, and Ticket Links as the hook points, and the spec's list of causes doesn't include Project deletion, so it is left out here and raised as an open question.
- **No new stream code.** `streamedActivity` already sends a fresh snapshot for any Activity with a Ticket, so `ticket.blocked`/`ticket.unblocked` carry the dependent's view, including `blocked`, with no server change. Adding them to the web's snapshot-carrying kinds is web work (07-08).
- **Tests in `apps/server/test/blocked.test.ts`.** Blocked through each blocker change, the filter matrix with status and search as both a User and an Agent, Claim, assign and move, a table of every transition cause (including the no-flip cases), and the stream. `ticket-links.test.ts`'s "records linking and unlinking on both Tickets" now filters to Link Activity, since a Blocks Link adds a transition on the blocked Ticket.

## 07-05 Ticket Links and Blocked over MCP

- **Both tools return the requesting Ticket's Links after the change.** `link_tickets` and `unlink_tickets` answer `{ links }` (from `listLinks`, as seen from `key`) rather than the one new Link or nothing, so the shape is the same for both and the Agent sees the Ticket's surroundings without a follow-up get_ticket. The Markdown leads with one confirmation sentence read from `key` ("CB-2 is now blocked by CB-1.", "CB-1 and CB-2 are no longer linked.") and then the grouped section. This costs one extra read per call.
- **Annotations are `readOnlyHint: false, destructiveHint: false`, with no `idempotentHint`.** Repeating either call fails (the existing Link conflict, or "aren't linked"), so neither is idempotent in the MCP sense.
- **Refusals reuse the domain's messages unchanged** through the existing tool error path. The Claim conflict's `blockers` array (07-04) stays REST-only: MCP tool errors carry only text, and the message already names the blockers.
- **`target` gets its own `targetKeyParam`** in `params.ts`, upper-cased like `ticketKeyParam` but described as the other Ticket's key.
- **get_ticket `links` is a flat array in group order, each with `kind`,** the same shape and order as `GET /api/tickets/:key/links`, rather than an object keyed by group. The grouping lives in the order and in the Markdown. Each Link's `createdBy` carries the User's email like every other MCP Actor, by passing Links through `withEmails`.
- **The Markdown heading is "Linked tickets", with "Blocked by", "Blocks", and "Related" subheadings.** A heading "Links" would be fine on its own, but GLOSSARY.md avoids "link" (for Parent) and `scripts/check-copy.mjs` flags it in any prose string, as 07-03 found. Empty groups are left out; a Ticket with none says "No linked tickets.".
- **A Link line is its own `linkLine`, not `ticketLine`.** `ticketLinkView` has no priority, Estimate, Blocked, or Assignee, so the line keeps the ticket-line shape with what it has: `**CB-3** [task, To Do] Title`, plus "archived" among the facts for an archived counterpart. Getting full Ticket views for every counterpart would need a new domain read for no story that asks for it.
- **"blocked" is the last fact on a ticket line,** after "N pts", so `[task, To Do, medium, 3 pts, blocked]`. Summaries gain only `blocked`, not `blockedByCount`, as the spec lists; the count is on get_ticket's full view.
- **get_ticket also says "Blocked: yes" in its fact list when Blocked,** next to "Archived: yes" and shown only when true. This also reaches claim, move, assign, and update output, which share `ticketMarkdown`. The open blockers are the "Blocked by" lines whose Status isn't Done and that aren't archived.
- **list_tickets takes `blocked` as a JSON boolean,** not the REST query string's `"true"`/`"false"`, since MCP arguments are JSON. Its description tells Agents to pass `blocked: false` with status todo and assignee unassigned when looking for work to claim, and the board resource's description says Blocked tickets are marked.
- **The web app's Agent prompt (`apps/web/src/lib/agent-setup.ts`) is unchanged.** Its step 1 still says list_tickets with status todo and assignee unassigned; adding `blocked: false` there is web work outside this card. Without it, an Agent following the prompt may pick a Blocked Ticket first and have Claim refuse it.
- **Tests in `apps/server/test/mcp-links-and-blocked.test.ts`.** The Agent acts over MCP; setup and the read-back of Links run as the User over REST. `mcp-agent-loop.test.ts`'s tool list now includes the two new tools.

## 07-06 Estimate in the web UI

- **Card badge sits in the top-right group**, after Archived and the loud priority, as an outlined muted pill ("3 pts"). It is quieter than the priority pills (border and muted text, no fill), so it reads as a fact rather than a warning, and it uses theme tokens only, so dark mode needs nothing extra. "0 pts" shows, since zero is a size (07-02). With Archived, Urgent, and "100 pts" all at once the badges wrap below the Ticket Key on a narrow lane; the row already wrapped that way for Archived plus Urgent.
- **The server is the only range check in Ticket detail.** The field sends whatever number is typed (`101`, `2.5`, `-1`) and the panel shows the server's refusal in its existing alert, then the field goes back to what the server holds, as the selects do. The text matches the shared `ticketEstimate` message anyway, but this way the detail never shows a message the server wouldn't. The create dialog keeps its existing pattern of parsing with `createTicketInput` first, which carries the same message.
- **Unchanged means no request.** Blur or Enter with the same value (or a field never edited) sends nothing, so no empty `ticket.updated` is recorded. A ref guards against Enter and the following blur both saving.
- **Unreadable input is dropped, not saved as blank.** A `type="number"` field reports text it can't parse (a lone "e") as an empty value; the field checks `validity.badInput` and reverts instead of clearing the Estimate. In the create dialog the same input simply leaves the Estimate blank, which loses nothing.
- **Escape in the field discards the draft.** The panel already keeps Escape in an input from closing it.
- **Placeholder "None"** says the Estimate is blank (story 9), matching "No parent" and "Unassigned" and get_ticket's `Estimate: none`. A "pts" suffix sits inside the field, `aria-hidden` since the label already names it; the browser spin buttons are hidden so they don't sit under it.
- **One `EstimateInput`** (`apps/web/src/components/estimate-input.tsx`) is shared by the detail field and the create dialog, so the range attributes, numeric keypad, suffix, and 44px phone height stay the same in both.
- **Fields grid goes to four columns on desktop.** Status, Priority, Type, Estimate fit one row of the 2xl panel; on a phone they are two rows of two, so Type no longer spans the full width. Assignee and Parent stay full width.
- **Create dialog puts Estimate beside Parent** in a `minmax(0,1fr) 7rem` row, so Parent keeps most of the width for long titles and the dialog gains no extra row.
- **Timeline reads numbers for `estimate`.** Other field diffs are strings, so `describeChange` has an `estimate` branch that treats only null as blank, so "set the estimate to 0" is not read as "cleared".
- **Live updates needed no code.** An Estimate change is a `ticket.updated` diff, which already carries the Ticket snapshot to open boards; the e2e covers it.
- **E2E in a new `e2e/estimate.spec.ts`** rather than `ticket-detail.spec.ts`, so the Links and Blocked UI work editing that file in parallel doesn't conflict. It covers the card badge (set, zero, blank, live set and clear), the create dialog, detail edits on Enter and blur with the Timeline wording, a no-op blur, refusals, and 375px layout with a 44px field.
- **Pre-existing failure, not from this card:** `board.spec.ts` "fits the viewport ... all show on a desktop" fails on desktop-light on the integration branch without these changes (the Done lane is about 96% in view).

## 07-08 Blocked on the board

- **The marker is an outlined amber pill with a lucide `Lock` and the word "Blocked".** Outlined so it never reads as one more step on the filled priority scale (orange High, red Urgent), and amber rather than red because Blocked is a wait, not an alarm. Amber and the lock also keep it apart from 07-06's muted outlined Estimate pill. It sits in the card's top-right badge group after Archived and before priority and the Estimate, so the existing wrapping rule keeps the Ticket Key on one line at 375px.
- **Accessible name and hover text come from `blockedByCount`.** The pill is `role="img"` with `aria-label` and `title` both "Blocked by N ticket(s)", like the Type icon and the Agent icon on the same card. The visible word stays "Blocked", short enough for a phone card; the count is in the label and on hover (story 36).
- **The card stays a pure function of the Ticket.** `BlockedMarker` takes only the count and is rendered from `ticket.blocked`; no Links are fetched for the board.
- **Live kinds.** `ticket.blocked` and `ticket.unblocked` join `ticketChanges` in `lib/live-events.ts`, so the snapshot goes into every cached view and someone else's change gets the usual live highlight. `ticket.linked` and `ticket.unlinked` join `activityKinds` only: their snapshot is applied, but the card shows nothing new from a Link itself, so they don't highlight (any Blocked flip arrives as its own event). 07-07 adds the open detail's Links invalidation for those two.
- **The URL says `blocked=only` or `blocked=hide`,** as the filter reads, rather than the list endpoint's `true`/`false`, the same way `archived=true` maps to `include`. `toBoardFilters` turns them into `blocked=true`/`false` for the request, and `BoardFilters.blocked` keeps the endpoint's values. Any other value is dropped and the board shows both, like every other filter.
- **`ticketMatchesFilters` judges `blocked`,** so a filtered view drops a Ticket the moment its `ticket.unblocked` snapshot arrives under "Only blocked" (and the reverse under "Hide blocked") without a refetch.
- **Labels.** The select is "Blocked" with "Any", "Only blocked", and "Hide blocked". It sits after Team and before "Show archived", so on a phone the six dropdowns fill three rows of two.
- **Known limit: the count can go stale live.** 07-04 records `ticket.blocked`/`ticket.unblocked` only when a dependent's Blocked state flips. When one of two open blockers is finished, the dependent stays Blocked, no Activity is recorded on it, and an open board keeps saying "Blocked by 2 tickets" until the next snapshot of that Ticket or a reload. The marker itself is always right. Fixing it means recording Activity (or streaming a snapshot) on a count change, which the spec rules out ("only on dependents whose state actually flipped"), so it is raised as an open question rather than changed here.
- **Tests.** `e2e/live.spec.ts` covers the marker appearing and clearing as an Agent moves the blocker to Done and back over MCP, with no board refetch. `e2e/filters.spec.ts` covers the label with one and two blockers, an unblocked card showing nothing, both filter choices in the URL with reload, search, and Clear filters, a filtered view taking an unblocked/blocked snapshot, an unknown URL value, and the 44px height of the new select on a phone. `linkTickets` joins `e2e/helpers.ts`. Checked by screenshot at 1280px light and 375px dark.
